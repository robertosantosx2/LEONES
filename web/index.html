LOAS — Libre-Open Agentic Stack

IA agéntica Libre/Open para hardware de consumo.

LOAS busca identificar y construir una pila agentic que pueda ejecutarse realmente en hardware de consumo, con especial prioridad al software Libre/Open y, dentro de él, Copyleft.

Ideas fundamentales

Un agente no existe para producir tokens: existe para completar objetivos. Por eso LOAS separa inferencia de Agentic y mide tareas reales con LOTB.

CABE una configuración puede ejecutarse razonablemente. RULA una configuración ha sido ejecutada y medida. Los resultados oficiales deben ser reproducibles.

LOTB: B01 memoria/localidad · B02 archivos · B03 multietapa · B04 recuperación ante fallo · B05 coding local.

Buddy: la pieza que mantiene unido el conocimiento

En LOAS, Buddy se entiende como la capa que ayuda al agente a trabajar con un conocimiento y un contexto controlados: qué sabe, qué documentos puede utilizar, qué información debe conservar y cómo recuperar ese conocimiento durante una tarea. No debe confundirse con el modelo de inferencia: el modelo puede cambiar mientras el conocimiento controlado permanece.

Usuario / objetivo→Buddy
conocimiento + contexto→Harness / agente→Modelo→Herramientas / resultado

La idea práctica es desacoplar lo que el sistema sabe de la pieza que genera los tokens. Buddy puede aportar el contexto controlado al agente y éste utilizar el modelo, backend o hardware que corresponda.

Nota: esta sección describe el papel arquitectónico que LOAS quiere dar a Buddy; los detalles concretos de cada integración deben verificarse contra la versión del proyecto que se esté utilizando.

La ventaja: el conocimiento no depende de la máquina

Una de las ideas centrales de LOAS es que cambiar la pila no debería obligarnos a perder el conocimiento acumulado. Podemos cambiar de CPU, añadir o quitar GPU, pasar de 16 a 64 GB, cambiar de portátil, cambiar el modelo, la cuantización, el backend o incluso partes del harness y mantener separada la capa de conocimiento controlado.

Hoy

i5 + 16 GB + modelo A + backend A

Mañana

i7 + 64 GB + GPU + modelo B + backend B

Lo que permanece

Conocimiento, estructura, documentos, criterios y memoria controlada.

Esto permite que una mejora de hardware sea una mejora de capacidad de ejecución, no una migración completa del conocimiento. También permite probar nuevas piezas de la pila sin convertir cada cambio en un proyecto de reconstrucción.

Por eso metaLOAS debe registrar por separado hardware, modelo, backend, harness y resultados: así podemos cambiar cualquiera de ellos y seguir comparando el mismo conocimiento y las mismas tareas.

Instalación

La forma básica es clonar el repositorio y trabajar con Python 3. La pila de inferencia utiliza llama.cpp y modelos GGUF; Buddy y el resto de componentes se incorporan según la configuración elegida.

git clone https://github.com/robertosantosx2/LOAS.git
cd LOAS
python3 --version
python3 -m pip install matplotlib

Para publicar resultados metaLOAS en GitHub se necesita GitHub CLI autenticado:

gh auth login

Distintas ejecuciones

1 · Diagnóstico metaLOAS

python3 scripts/metaloas-report.py

Extrae hardware y software básico y crea un Markdown sin datos personales.

2 · Publicar metaLOAS

python3 scripts/metaloas-report.py --model ~/modelo.gguf --publish

3 · Inferencia

Mide tok/s, memoria y estabilidad e identifica modelo, cuantización y commit.

4 · LOTB agentivo

python3 scripts/lotb-agentic-test.py

Ejecuta B01–B05 contra el endpoint local.

5 · Estadísticas

python3 scripts/metaloas-stats.py

Agrega informes y genera gráficas.

Tiempo estimado por tarea

La referencia de LOAS pasa de ser exclusivamente tok/s a ser el tiempo necesario para completar una tarea. Las cifras siguientes son estimaciones iniciales, no mediciones oficiales. Cuando haya suficientes datos metaLOAS, serán sustituidas por tiempos observados.

UX LOAS

< 5 s · excelente

5–10 s · muy buena

10–30 s · buena

30–60 s · aceptable

1–3 min · lenta

> 3 min · no mínimamente usable

B01 · Memoria/localidad

5–15 s

Mantener contexto y continuar una tarea.

B02 · Archivos

10–30 s

Leer, modificar y devolver un archivo.

B03 · Multietapa

20–60 s

Completar una secuencia de acciones.

B04 · Recuperación

30–120 s

Detectar un fallo, corregirlo y continuar.

B05 · Coding local

30–180 s

Analizar, editar y comprobar código.

Importante: una pila que supere 10 tok/s no garantiza una buena UX. También cuentan los pasos agentivos, llamadas a herramientas, latencia, errores y reintentos. metaLOAS debe medir el tiempo total de tarea y el resultado PASS/FAIL.

metaLOAS: contribuir

Los resultados describen el experimento, no a la persona. No se deben publicar nombres, emails, usuarios, hostnames identificables, seriales, UUID, MAC/IP, ubicación, rutas personales, credenciales o tokens.

python3 scripts/metaloas-report.py --model ~/modelo.gguf --publish

Los resultados pueden clasificarse como reported → reproducible → verified; la web debe distinguir siempre mediciones observadas de estimaciones.
