1. Qué es LEONES

LEONES — Local Ecosystem of Open Neural Expert Systems estudia qué combinación de hardware y software Libre/Open permite convertir una máquina de consumo en un sistema agentic realmente útil.

Principio rector: LEONES mide sistemas, no solo modelos. Un agente existe para completar objetivos, no simplemente para producir tokens.

Libre

La libertad del software importa más que el precio cero.

Open

Se descubren piezas abiertas según criterios compatibles con OSI.

Copyleft

Entre alternativas comparables, LEONES prioriza Copyleft.

2. La pila completa

HARDWARE
   ↓
SISTEMA OPERATIVO
   ↓
RUNTIME / DRIVERS
   ↓
BACKEND DE INFERENCIA
   ↓
MODELO + CUANTIZACIÓN
   ↓
HARNESS / AGENTIC STACK
   ↓
HERRAMIENTAS / SKILLS
   ↓
BUDDY / KNOWLEDGE
   ↓
LOTB
   ↓
RESULTADO + UX

La primera referencia incluye Buddy, Hermes, LangGraph, llama.cpp y GGUF. La pila se congela para poder medirla, no porque se considere óptima para siempre.

CABE y RULA son términos operativos del proyecto: primero se determina si una configuración cabe en el hardware y después si realmente rula/funciona bajo las pruebas.

Ubuntu es una referencia práctica para experimentar con CPU, GPU y runtimes locales.

Red Hat / RHEL

RHEL / Red Hat
 ├─ paquetes del sistema
 ├─ drivers
 ├─ Python / entorno
 ├─ runtime
 ├─ backend
 ├─ modelo
 ├─ harness + Buddy
 └─ LOTB

La arquitectura no cambia. Cambian la gestión de paquetes, drivers y detalles del entorno.

4. LOTB · Local Open Tool/Agent Benchmark

LOTB separa la evaluación de inferencia de la evaluación agentic.

NivelQué mide
Inferenciaprompt evaluation, generation tok/s, memoria, estabilidad y tiempo total.
Agenticéxito de tareas, tool calls, errores, tiempo de tarea y cumplimiento del objetivo.

Batería inicial

B01

Memoria / localidad

Contexto y recuperación local.

B02

Archivos

Operación sobre ficheros y herramientas.

B03

Multietapa

Planificación y ejecución de varios pasos.

B04

Recuperación

Comportamiento ante fallo.

B05

Coding local

Generar, modificar y ejecutar código local.

Baseline LOTB-0: Qwen3-8B Q4_K_M GGUF. Se comparan también Qwen3-8B Q5_K_M, Q8_0 y Qwen3-14B Q4_K_M en perfiles con más memoria.

5. Reingeniería de scripts

Cada script debe hacer pocas cosas, muy claras y bien documentadas. Puede llamar a otros scripts; no debe convertirse en un orquestador monolítico.

hardware → model → infer → LOTB → report → publish → stats

hardware

Extrae CPU, RAM, GPU y software básico de la máquina.

model

Identifica modelo, formato, cuantización y hash cuando sea posible.

infer

Mide inferencia nativa contra el backend.

lotb

Ejecuta las tareas agentivas estandarizadas.

report

Genera el informe Markdown y el resultado estructurado.

publish / stats

Publica y agrega resultados para el dashboard.

6. Prospección continua

DIARIA

Nuevas piezas Open

Buscar nuevos proyectos que aparezcan en el futuro. Descubrir tanto piezas Open según criterios OSI como Copyleft.

Regla congelada: se descubren las piezas Open; LEONES simplemente prioriza las Copyleft.

SEMANAL

Harnesses y skills

Investigar proyectos que mejoren las skills, funciones o características de los harnesses. Los compatibles con la pila se muestran en un menú de recomendaciones.

descubrir → clasificar → comprobar licencia → comprobar compatibilidad → evaluar utilidad → recomendar

7. Recomendador de pila y mejora de UX

HARDWARE + OS + BACKEND + MODEL + HARNESS + BUDDY + LOTB
                         ↓
                 análisis de cuello de botella
                         ↓
        ┌────────────┬────────────┬────────────┐
        ↓            ↓            ↓            ↓
      modelo       backend      harness      tools
        └────────────┴────────────┴────────────┘
                         ↓
                 recomendación al usuario
                         ↓
                     re-evaluar

LEONES debe poder explicar qué pieza de la pila merece cambiarse para mejorar la UX: modelo, backend, harness, herramientas, etc. La recomendación debe distinguir entre medición, evidencia e hipótesis.

No se optimiza tok/s aisladamente. La métrica principal es la capacidad de completar tareas útiles con una latencia razonable.

8. manada_leones

manada_leones convierte las ejecuciones locales en conocimiento público y acumulativo sin exigir telemetría personal.

máquina
  ↓
diagnóstico automático
  ↓
result.json + report.md
  ↓
directorio de resultados
  ↓
GitHub
  ↓
estadísticas
  ↓
dashboard web

Se almacenan informes técnicos en un directorio común para poder agregarlos, generar estadísticas y mostrar gráficas.

No publicar: nombres, emails, usuarios, hostnames identificables, números de serie, UUID, MAC/IP, ubicación exacta, rutas personales, credenciales o tokens.

9. Evidencia y confianza

reported → reproducible → verified
                    ↘ rejected

Reported

Existe un informe aportado.

Reproducible

Hay información suficiente para repetirlo.

Verified

La evidencia ha sido comprobada.

Rejected

No debe conservarse como evidencia válida.

Los benchmarks de terceros sirven para investigar y formular hipótesis. Un resultado oficial LEONES debe proceder de una medición propia, reproducible y trazable.

10. Instalación y primera ejecución

git clone https://github.com/robertosantosx2/LEONES.git
cd LEONES
python3 --version
python3 scripts/leones.py hardware
python3 scripts/leones.py model modelo.gguf
python3 scripts/leones.py infer --url http://127.0.0.1:8080/v1/chat/completions --model local-model
python3 scripts/leones.py lotb --endpoint http://127.0.0.1:8080

Después se genera el informe y, si el usuario lo decide, se publica. La publicación nunca debe incluir secretos ni datos personales.

12. Conocimiento que sobrevive

La razón de separar Buddy del resto de la pila es preservar el conocimiento controlado aunque mañana cambien CPU, GPU, sistema operativo, backend, modelo o harness.

HOY:  máquina A + pila A + conocimiento
                    ↓
CAMBIO: hardware / OS / backend / modelo / harness
                    ↓
MAÑANA: máquina B + pila B + MISMO CONOCIMIENTO
