Recorrido operativo canónico

Cómo se opera LEONES hoy: del hardware observado a la evidencia, sin mezclar estimaciones con mediciones.

LEONES · Operación
Identidad funcional del ecosistema
Prospección Atlas Router Hardware Agents / LOTB Manada

1 · Autoridad

LEONES descubre el hardware. Hermes aporta ecosistema runtime/model-fit; OMH organiza. El usuario elige Magnitude u ODS. LEONES verifica, mide y sentencia.

LLMFit/FitLLM queda fuera del camino RC3: no es dependencia de arranque ni selector canónico.

2 · Camino canónico

UBUNTU REAL
   ↓
scripts/hardware_profile.py → hardware-profile.v1
   ↓
RC3 adapter + Hermes/OMH hints
   ↓
candidate-set.v1 + evidencia externa (HF / AA)  [ESTIMATED / reported]
   ↓
usuario elige modelo + Magnitude | ODS
   ↓
consentimiento → preparar/instalar → verificar (OBSERVED)
   ↓
tareas LEONES → medición → evidencia (MEASURED)

3 · Sonda y gate

  • Sonda única: scripts/hardware_profile.py
  • Contrato: scripts/rc3_hardware_discovery.py → hardware-profile.v1
  • Gate estático: scripts/rc3_release_gate.py (no declara handoffs ni benchmarks físicos)

4 · Stacks

Magnitude

Se activa solo si el usuario lo elige. LEONES no sustituye su CLI ni su servicio.

ODS

Se activa solo si el usuario lo elige. Un ods status verde es OBSERVED, no MEASURED LEONES.

5 · Medición

La medición LEONES exige runtime y artefacto disponibles, consentimiento y ejecución controlada. Métricas como wall_seconds o measured_tps solo tras esa ejecución, con procedencia.

RC1 aporta el pipeline efectivo de ejecución/evidencia cuando el camino de runtime está resuelto. A01 u otras tareas no convierten un smoke externo en evidencia LEONES por sí solas.
