Prospector descubre. Atlas conserva conocimiento. Task Intelligence interpreta la necesidad. Router decide. Quant y Fine-Tuning adaptan. Agents actúa. Runtime ejecuta. Benchmark & Evaluation mide y devuelve evidencia al sistema.

ACTIVO · diarioPILAR 1

Prospector

Descubre qué está cambiando. Rastrea modelos, runtimes, harnesses, skills, cuantizaciones, eficiencia, hardware y benchmarks.

Evolución: más fuentes → clasificación → detección de cambios → priorización para revisión.
ACTIVO · en evoluciónPILAR 2

Atlas

Conserva el conocimiento estructurado. Modelos, familias, organizaciones, licencias, formatos, hardware, runtimes, benchmarks y evidencia con procedencia.

external-unvalidated → revisión → evidencia Atlas.
INICIALPILAR 3

Task Intelligence

Entiende qué se quiere conseguir. Convierte una petición humana en requisitos operativos: contexto, herramientas, memoria, RAG, shell, filesystem, latencia o verificación.

Qué puede esperar el usuario: una tarea bien descrita antes de elegir modelo o hardware.
INICIAL · transparentePILAR 4

Router

Decide qué pila utilizar. Combina tarea, hardware, modelo, cuantización, backend y evidencia.

Evolución: reglas → restricciones reales → evidencia de Atlas → optimización multiobjetivo.
INICIALPILAR 5

Quant

Adapta la representación del modelo. Evalúa calidad ↔ memoria ↔ velocidad y conserva trazabilidad.

Para el usuario: reducir memoria no es gratis; hay que medir el impacto sobre calidad y rendimiento.
INICIALPILAR 6

Fine-Tuning

Adapta modelos a necesidades concretas. Incluye PEFT, LoRA y QLoRA cuando proceda.

Regla: primero hay que demostrar que el problema requiere adaptación; no todo problema necesita fine-tuning.
INICIALPILAR 7

Agents

Convierte el modelo en capacidad de acción. Planificación, herramientas, memoria, RAG, workflows, tool-calling y recuperación ante errores.

Objetivo: completar objetivos, no simplemente producir tokens.
INICIAL · backend independientePILAR 8

Runtime

Ejecuta localmente. Abstrae los motores de inferencia para que LEONES no dependa de una aplicación concreta.

Ejemplos de la pila: llama.cpp, Ollama, Transformers, vLLM, MLX y otros motores según hardware y objetivo.
ACTIVO · Evaluación en evoluciónPILAR 9

Benchmark & Evaluation

Mide y produce evidencia. Incluye inferencia, memoria, latencia, estabilidad y evaluación para tareas agentivas.

El resultado vuelve a Atlas y, con suficiente evidencia, mejora Router.
Bucle de aprendizaje

Cómo se relacionan

DESCUBRIR → CONOCER → ENTENDER → DECIDIR → ADAPTAR → ACTUAR → EJECUTAR → MEDIR
    ↑                                                                  ↓
    └──────────────────────────── APRENDER ← EVIDENCIA ─────────────────┘

Los estados de los pilares no significan que una capacidad no exista en el repositorio: indican el grado de madurez de su implementación como componente del ecosistema.

Cómo debe usarlo una persona

Si solo quieres ejecutar un LLM

Empieza por Hardware → Atlas → Runtime → Evaluación.

Si quieres un agente

Empieza por Task Intelligence → Router → Agents → Runtime → Evaluación.

Si quieres investigar

Empieza por Prospector → Atlas → Benchmark & Evaluation.

Si quieres aportar datos

Usa las herramientas locales y la ruta de Manada; compartir resultados debe ser voluntario y respetar privacidad.
