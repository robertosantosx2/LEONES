LEONES · Evaluación

Evaluar sistemas, no solo modelos.

Qué mide

Evaluación mide la capacidad de una combinación local de modelo, backend, harness y herramientas para completar objetivos.

Prueba Interés
B01 Memoria, localidad y contexto
B02 Archivos y herramientas
B03 Tareas multietapa
B04 Recuperación y conocimiento
B05 Coding y ejecución local

Evidencia

reported → reproducible → verified
                    ↘ rejected

Regla: publicar un resultado no lo convierte automáticamente en verificado.

Cómo evaluar

Un protocolo que se pueda repetir

Define la carga

Fija modelo y cuantización, versión del runtime, flags, hardware, longitudes de entrada/salida, concurrencia y si existen prefijos compartidos o salidas estructuradas.

Mide varias dimensiones

No uses solo tok/s. Registra TTFT, TPOT, p50/p95/p99, tokens/s, solicitudes/s y memoria cuando sea posible.

Usa tareas representativas

La documentación recomienda un conjunto pequeño de 30–100 prompts que representen las tareas reales del usuario.

Separa desarrollo y prueba

El conjunto de prueba no debe convertirse en objetivo de optimización. Una vez que se ajusta el sistema contra él, deja de ser una prueba limpia.

Integridad de la evaluación

Regla de oro: entrenamiento → validación → prueba. La prueba debe permanecer reservada para medir generalización.

Hay riesgos específicos de LLM: contaminación del preentrenamiento, datos sintéticos, recuperación que contiene respuestas, sobreajuste de prompts/scaffolds y contaminación de benchmarks de código. Para afirmaciones serias, conviene usar pruebas frescas, privadas o en vivo y documentar protocolo, incertidumbre y limitaciones.

Por qué importa para Router

Dos modelos con una velocidad similar pueden tener una utilidad completamente distinta para una tarea agentiva. Evaluación aporta la evidencia que falta a una simple medición de tok/s.
