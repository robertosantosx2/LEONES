# Tandem.cpp + Qwen3.5-35B-A3B — RTX 3050 baseline (2026-11-05)

**Classification:** Experimental · physical measurement on one Ubuntu workstation · baseline for the 512 vs 768 MiB MoE cache test.

## Hardware
- MSI Thin 15 B12UC; Intel Core i7-12650H, 16 logical CPUs.
- 14 GiB RAM; NVIDIA RTX 3050 Laptop GPU, 4 GiB VRAM, sm_86.
- Driver 580.178.04; local CUDA toolkit 13.4; Ubuntu.

## Software and model
- Tandem workspace: `$HOME/tandem-qwen35-test-20261103`.
- llama.cpp fork base commit: `f5222f25c` (2026-10-28); binary reports `0.8.0-dev (build 11962)`.
- CUDA build target sm_86; build log: `tandem-build.log`.
- Model: `bartowski/Qwen_Qwen3.5-35B-A3B-GGUF`, `Qwen_Qwen3.5-35B-A3B-IQ2_XXS.gguf`, 10,676,139,840 bytes (~9.94 GiB), GGUF v3, architecture `qwen35moe`.
- Metadata: 35B total / A3B active; 256 experts, 8 active/token; 41 trunk layers; embedding 2048; metadata context 262,144.
- IQ2_XXS is an extremely aggressive quantization. This test demonstrates feasibility and speed, not independently validated answer quality.

## Exact runtime baseline
Server: `http://127.0.0.1:18085`; observed PID `1424218`.
Log: `$HOME/tandem-qwen35-test-20261103/qwen35-hybrid-512.log`.

```bash
nohup env \
  LLAMA_MOE_CPU=auto \
  LLAMA_MOE_CPU_THREADS=7 \
  "$BIN" \
  --model "$MODEL" \
  --host 127.0.0.1 \
  --port 18085 \
  --cpu-moe \
  --moe-cache-mib 512 \
  --ctx-size 1024 \
  --batch-size 128 \
  --ubatch-size 64 \
  --parallel 1 \
  --threads 8 \
  --threads-batch 8 \
  --fit on \
  > "$LOG" 2>&1 < /dev/null &
```

Default `/usr/local/bin/llama-server` and `llama-cli` were not modified. TensorFold and Hermes were not modified.

## Inference evidence
Requests used `"chat_template_kwargs": {"enable_thinking": false}` to obtain normal assistant text.

| Test | Prompt tokens | Generated | Generation speed |
|---|---:|---:|---:|
| 256-token run 1 | 52 | 256 | 33.558 tok/s |
| 256-token run 2 | 4 (cache hit) | 256 | 38.770 tok/s |
| 256-token run 3 | 4 (cache hit) | 256 | 38.265 tok/s |
| 512-token run | 52 | 512 | 37.957 tok/s |

Mean generation speed across these four runs: **37.14 tok/s**. The 512-token request returned HTTP 200, generated 512 tokens in 13.463 s and finished with `length` because it reached the requested token limit. Prompt processing numbers are not directly comparable because prompt-cache hits changed the effective prompt token count. These are short-run observations, not a sustained benchmark.

## Memory and GPU evidence
- Corrected `/proc/PID/smaps` parsing identified the GGUF mapping at 7,376.1 MiB RSS/PSS, 0 MiB swap. The full 9.94 GiB file was not resident; the mapping shows only the resident portion.
- Process `smaps_rollup`: RSS 8,642,360 kB; PSS 8,636,728 kB; anonymous PSS 986,704 kB; file PSS 7,650,000 kB; swap 424,420 kB (~414.5 MiB).
- Heap region: 258 MiB RSS, 216.8 MiB swap. Other anonymous regions also held some swap. The GGUF mapping itself had no swapped pages in that capture.
- Ten samples at 2-second intervals were identical: RSS 8,357.7 MiB; anonymous RSS 937.5 MiB; file RSS 7,394 MiB; process swap 414.4 MiB.
- Global memory snapshot: MemAvailable ~10.1 GiB; swap total 32 GiB, free ~23.9 GiB; global swap used ~8.06 GiB. Earlier `vmstat` showed almost no sustained swap-out after the first aggregate row, `wa=0`, and PSI avg10=0.00. Global swap used includes other processes and historical swapped pages.
- Idle GPU snapshot: 2,077 MiB used, 1,692 MiB free, 0% utilization, 47 °C. Earlier during inference monitoring, GPU utilization reached 76% and temperature was about 54 °C.
- HTTP health repeatedly returned `{"status":"ok"}`.

## Interpretation and limits
Demonstrated: model load, normal text generation with thinking disabled, a completed 512-token response, ~37–38 tok/s short-run generation, stable process memory over a 20-second idle sample, and a healthy HTTP endpoint.

Not demonstrated: long-duration leak-free operation, quality versus higher-bit quantizations, larger contexts, concurrent requests, optimal cache size, or full GGUF residency. The 20-second memory sample is not a long-run stability test. The 0% GPU snapshot was taken after inference and does not imply the GPU was unused during generation.

## Completed experiment: 512 vs 768 MiB MoE cache

The comparison changed only `--moe-cache-mib` (512 vs 768 MiB). Model, server port, context, batch sizes, CPU thread settings, prompt and generation parameters were kept the same.

### 768 MiB inference results

All requests used `enable_thinking=false`, temperature 0.2 and the same Spanish prompt.

| Test | Prompt tokens | Cached prompt tokens | Generated tokens | Generation time | Generation speed |
|---|---:|---:|---:|---:|---:|
| 256-token run 1 | 52 | 0 | 256 | 9.943 s | 25.645 tok/s |
| 256-token run 2 | 52 | 48 | 256 | 7.732 s | 32.979 tok/s |
| 256-token run 3 | 52 | 48 | 256 | 6.980 s | 36.534 tok/s |
| 512-token run 1 | 52 | 48 | 512 | 14.297 s | 35.741 tok/s |
| 512-token run 2 | 52 | 48 | 512 | 14.354 s | 35.601 tok/s |

Mean generation speed:
- 256-token tests: **31.72 tok/s**.
- 512-token tests: **35.67 tok/s**.

All five requests returned `finish_reason=length`, as expected because they reached their requested output-token limits.

### Direct comparison

| Metric | 512 MiB baseline | 768 MiB configuration |
|---|---:|---:|
| 512-token generation speed | 37.957 tok/s (one run) | 35.671 tok/s (mean of two) |
| 256-token generation speed | 33.558 / 38.770 / 38.265 tok/s | 25.645 / 32.979 / 36.534 tok/s |
| Initial/observed VRAM | 2,077 MiB idle snapshot | 2,245 MiB after startup; 2,345 MiB after generation |
| Server health | HTTP OK | HTTP OK |

The 768 MiB 512-token mean is approximately **6.0% slower** than the single 512 MiB reference run. This is a small sample and does not establish a statistically robust performance regression. The 256-token runs also show substantial run-to-run variation, so the cache-size comparison should not be interpreted as a controlled statistical benchmark.

### 768 MiB memory and stability observations

Final snapshot after inference:
- Tandem process RSS: 9,268,800 kB (approximately 8.84 GiB).
- GPU memory: 2,345 MiB / 4,096 MiB; Tandem process accounted for 2,322 MiB.
- GPU temperature: 51 °C; utilization was 0% in the post-inference snapshot.
- `MemAvailable`: 9.6 GiB.
- Global swap used: approximately 7.5 GiB.
- Memory PSI: `avg10=0.10` for both `some` and `full`.
- HTTP health endpoint returned `{"status":"ok"}`.

A 10-second `vmstat` sample showed an initial aggregate row with `si=290`, `so=265`; subsequent samples had `so=0`, with small intermittent `si` readings (16–52). Swap occupancy remained approximately stable around 7.8 million KiB. This indicates limited intermittent swap-in during the observed interval, not sustained swap-out. The global swap figure is system-wide and is not attributable solely to Tandem.

The server was then stopped cleanly with `SIGTERM`; port 18085 no longer served HTTP. No default llama.cpp server, TensorFold or Hermes process was modified.

### Conclusion

Both cache sizes successfully loaded and ran this 35B-A3B IQ2_XXS model on the RTX 3050 4 GiB system. The 768 MiB configuration did not demonstrate a repeatable speed advantage over the 512 MiB baseline and used more VRAM. **Retain 512 MiB as the preferred measured configuration for this machine**, pending any future larger and repeated benchmark.

This remains a feasibility experiment, not a model-quality evaluation or a long-duration stability certification.
